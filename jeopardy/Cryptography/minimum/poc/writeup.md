# minimum Writeup

## Challenge Overview

We're given a server that implements a custom authenticated encryption scheme resembling AES-GCM. The server encrypts a known command (`STATUS_REPORT___`) and gives us the ciphertext + authentication tag. Our goal: forge a ciphertext that decrypts to `GIVEMETHEFLAG___` with a valid tag.

The server exposes three endpoints:
- **`encrypt`**  returns the encrypted known command (one-shot)
- **`verify`** checks if a `(ciphertext, tag)` pair is valid (max 100 queries)
- **`execute`**  decrypts if the tag is valid; returns the flag if the command is `GIVEMETHEFLAG___`

At first glance, this seems impossible since we don't know the AES key, the nonce is random, and the authentication key `H` is generated by a hidden `gen_auth_key()` function. But the vulnerability lies in **how H is generated**.

---

## Part 1: Understanding GHASH

### What is GCM?



AES-GCM (Galois/Counter Mode) combines two components:

1. **AES-CTR** for encryption, a stream cipher that XORs plaintext with a keystream
2. **GHASH** for authentication, a polynomial MAC that produces a tag

The critical insight: in CTR mode, **flipping a ciphertext bit flips the corresponding plaintext bit**. This is why the authentication tag exists  to detect tampering. If we could forge a valid tag for a modified ciphertext, the authentication is broken.

### How GHASH Works

GHASH is a polynomial evaluation over the finite field GF(2^128). It uses a secret 128-bit authentication key `H`.

Given ciphertext blocks C₁, C₂, ..., Cₘ, GHASH computes:

```
Y₀ = 0
Y₁ = (Y₀ ⊕ C₁) ⊗ H  =  C₁ ⊗ H
Y₂ = (Y₁ ⊕ C₂) ⊗ H  =  C₁ ⊗ H² ⊕ C₂ ⊗ H
Y₃ = (Y₂ ⊕ C₃) ⊗ H  =  C₁ ⊗ H³ ⊕ C₂ ⊗ H² ⊕ C₃ ⊗ H
...
```

where `⊗` is multiplication in GF(2^128) and `⊕` is XOR.

In general, the final GHASH output (before the length block and tag masking) is:

```
Yₘ = C₁ · H^m  ⊕  C₂ · H^(m-1)  ⊕  ...  ⊕  Cₘ · H
```

Each ciphertext block is multiplied by a **different power of H**. The final authentication tag is:

```
Tag = GHASH(C₁, ..., Cₘ, LenBlock) ⊕ AES_K(J₀)
```

where `AES_K(J₀)` is a mask derived from the nonce, and `LenBlock` encodes the data lengths.

### The Key Observation

Look at that polynomial carefully. Block `Cᵢ` is multiplied by `H^(m-i+1)`. If two different powers of H happen to be **equal**, say `H^a = H^b`, then the polynomial can't distinguish between the positions `a` and `b`.

**When does `H^a = H^b`?**

This happens when `H^(a-b) = 1`, which means the powers of H **cycle** with period `n = a - b`. In group theory, this period is called the **multiplicative order** of H, written `ord(H)`.

## Part 2: The Cycling Attack

### Where Things Break

> **If H = 0**, then Xₙ = 0 regardless of the Cᵢ values, and all messages have the same authentication tag.
>
> **If H = 1**, then the tag is just an XOR of the ciphertext blocks, and reordering the blocks gives the same tag.

But H = 0 and H = 1 are only 2 out of 2^128 possible values, a 2/2^128 = 1/2^127 chance. Surely that's too unlikely to exploit?

**Not so fast.**

> There are other weak values of H that belong to a **short cycle** when raised to the i-th powers. All values of H that belong to a short cycle of values and therefore many values of H that are weaker than they should be.

### Why GF(2^128) is Vulnerable

This is where Saarinen's paper *"Cycling Attacks on GCM, GHASH and Other Polynomial MACs and Hashes"* (2011/202) comes in.

The multiplicative group of GF(2^128) has order `2^128 - 1`. This number factors as:

```
2^128 - 1 = 3 × 5 × 17 × 257 × 641 × 65537 × 274177 × 6700417 × 67280421310721
```

This is a **smooth number**, it factors into 9 prime factors (which happen to be related to Fermat numbers). By Lagrange's theorem, the valid subgroup sizes are all **divisors** of `2^128 - 1`. Since there are 9 prime factors, there are `2^9 = 512` possible subgroup sizes.

This means there are elements H with multiplicative orders as small as:
- `ord(H) = 1`, only the identity element (1 element)
- `ord(H) = 3`, 2 elements
- `ord(H) = 5`, 4 elements
- `ord(H) = 15`, 8 elements
- `ord(H) = 17`, 16 elements
- ...and so on up to `ord(H) = 2^128 - 1` (the generator)

### The Attack: Block Swapping

From Section 3 of the paper:

> If we know that `H^(m-i+1) = H^(m-j+1)` with `i ≠ j`, we may simply swap ciphertext blocks `Xᵢ` and `Xⱼ` and the resulting authentication tag stays unmodified, which amounts to **message forgery**.

More precisely: swapping blocks at positions `i` and `j` preserves the tag if and only if:

```
H^(j - i) = 1   ⟺   ord(H) divides (j - i)
```

**Proof.** The change in GHASH from swapping blocks `i` and `j`:

```
ΔGHASH = (Cⱼ - Cᵢ) · H^(m-i+1) + (Cᵢ - Cⱼ) · H^(m-j+1)
       = (Cᵢ ⊕ Cⱼ) · H^(m-j+1) · (H^(j-i) ⊕ 1)
```

In GF(2), subtraction equals addition equals XOR. If `H^(j-i) = 1`, then `H^(j-i) ⊕ 1 = 1 ⊕ 1 = 0`, so `ΔGHASH = 0`. The tag doesn't change.

### Targeted Bit-Flip Forgery

Section 6 of the paper extends this to **targeted attacks**. Instead of just swapping blocks, we can apply the **same XOR delta** to two blocks at distance `ord(H)`:

```
C'ᵢ = Cᵢ ⊕ Δ
C'ⱼ = Cⱼ ⊕ Δ     where  ord(H) | (j - i)
```

The change in GHASH:

```
ΔGHASH = Δ · H^(m-i+1) ⊕ Δ · H^(m-j+1)
       = Δ · H^(m-j+1) · (H^(j-i) ⊕ 1)
       = Δ · H^(m-j+1) · 0
       = 0
```

The tag stays valid. Since AES-CTR is a stream cipher, XORing the ciphertext by `Δ` flips the corresponding plaintext bits. So:

- Block `i` now decrypts to `Pᵢ ⊕ Δ` (the value we want)
- Block `j` decrypts to `Pⱼ ⊕ Δ` (garbage, but we don't care)

This means we can **change the plaintext to anything we want** in one block, as long as we also modify a "sacrifice" block at distance `ord(H)` by the same delta.

## Part 3: Applying This to the Challenge

### Reading the Source Code

From the release `server.py`, we see:

```python
from secret import gen_auth_key
...
self.H = gen_auth_key()
```

The GHASH key H comes from a hidden function. We don't know its value, but we can use the `verify` oracle to **probe for cycling behavior**.

The server uses 20 ciphertext blocks (320 bytes). The GHASH processes 21 blocks total (20 ciphertext + 1 length block). Block `i` (0-indexed) is multiplied by `H^(21-i)`.

### Step 1: Determine ord(H)

We know from the source that H lives in GF(2^128). The hidden `gen_auth_key()` must produce an H with a short cycle, otherwise the verify oracle (100 queries) would be useless.

We don't need to know the exact set of possible orders. We just need one rule:

> Swapping blocks at distance `d` preserves the tag **if and only if** `ord(H)` divides `d`.

This means: if we test d=1, d=2, d=3, d=4, ... the **smallest d where the swap is accepted** equals `ord(H)`.

```python
order = None
for d in range(1, num_blocks):
    valid = verify(swap_blocks(ct, 0, d))
    if valid:
        order = d
        break
```

For example, if the swap is rejected at d=1, d=2, d=3, d=4 but accepted at d=5, then `ord(H) = 5`. We don't need to guess, and we don't need to know the server's internals. The oracle tells us directly.

With 20 blocks, the worst case is 19 queries to test every distance. Well within the 100-query limit.

### Step 2: Forge the Target Command

We know:
- Original plaintext block 0: `STATUS_REPORT___` (16 bytes)
- Target plaintext block 0: `GIVEMETHEFLAG___` (16 bytes)
- `ord(H) = n` (determined in step 1)

Compute the delta:

```python
delta = XOR(b"STATUS_REPORT___", b"GIVEMETHEFLAG___")
```

Apply the bit-flip forgery:

```python
C'[0] = C[0] ⊕ delta    # → decrypts to GIVEMETHEFLAG___
C'[n] = C[n] ⊕ delta    # → decrypts to garbage (sacrificed)
```

The tag stays valid because `H^n = 1`, so the two modifications cancel in the GHASH polynomial.

### Step 3: Get the Flag

Submit the forged ciphertext with the **original tag** via the `execute` endpoint. The server verifies the tag, decrypts, sees `GIVEMETHEFLAG___` in the first block, and returns the flag.

## Part 4: The Hidden Vulnerability — `gen_auth_key()`

Looking at the actual server source (not given to players), the key generation is:

```python
GROUP_ORDER = (1 << 128) - 1       # = 2^128 - 1
exp = GROUP_ORDER // 15            # = (2^128 - 1) / 15
r = random_nonzero_element()
H = gf_pow(r, exp)                 # H = r^((2^128-1)/15)
```

**Why does this guarantee a short cycle?**

By Fermat's Little Theorem for finite fields: for any nonzero `r` in GF(2^128):

```
r^(2^128 - 1) = 1
```

Therefore:

```
H^15 = (r^((2^128-1)/15))^15 = r^(2^128-1) = 1
```

So `ord(H)` **must divide 15**. The possible orders are {1, 3, 5, 15}.

The probability distribution (based on Euler's totient function):

| ord(H) | Probability | # of elements with this order |
|--------|-------------|-------------------------------|
| 1      | 1/15 ≈ 7%  | 1 (the identity element) |
| 3      | 2/15 ≈ 13% | 2 |
| 5      | 4/15 ≈ 27% | 4 |
| 15     | 8/15 ≈ 53% | 8 |

All of these are exploitable because our message has 20 blocks, and the maximum `ord(H) = 15` is well within range.

## Part 5: The Solver

```python
#!/usr/bin/env python3
from pwn import *
import json

io = remote("localhost", 13424)
io.recvuntil(b"\n"); io.recvuntil(b"\n")

def msg(obj):
    io.sendline(json.dumps(obj).encode())
    return json.loads(io.readline())

# ── Step 1: Get the encrypted message ──
data = msg({"option": "encrypt"})
known_cmd = data["command"].encode()
ct        = bytes.fromhex(data["ciphertext"])
tag_hex   = data["tag"]

# ── Step 2: Determine ord(H) ──
def split(bs): return [bs[i:i+16] for i in range(0, len(bs), 16)]
def swap(ct, i, j):
    b = split(ct); b[i], b[j] = b[j], b[i]; return b"".join(b)
def verify(ct_bytes):
    return msg({"option":"verify","ciphertext":ct_bytes.hex(),"tag":tag_hex}).get("valid")

# Test d=1, 2, 3, ... — smallest valid d = ord(H)
order = None
for d in range(1, 20):
    if verify(swap(ct, 0, d)):
        order = d
        break

log.success(f"ord(H) = {order}")

# ── Step 3: Forge GIVEMETHEFLAG___ ──
TARGET = b"GIVEMETHEFLAG___"
delta  = bytes(a ^ b for a, b in zip(known_cmd.ljust(16, b"\x00"), TARGET))

blks = split(ct)
blks[0]     = bytes(a ^ b for a, b in zip(blks[0], delta))
blks[order] = bytes(a ^ b for a, b in zip(blks[order], delta))

# ── Step 4: Get the flag ──
result = msg({"option":"execute","ciphertext":b"".join(blks).hex(),"tag":tag_hex})
log.success(f"FLAG: {result['flag']}")
```

**Total oracle queries: at most 19 (verify) + 1 (execute) = 20 queries.** Well within the 100-query limit.
